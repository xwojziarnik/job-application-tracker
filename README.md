# job-application-tracker

[![CI](https://github.com/xwojziarnik/job-application-tracker/actions/workflows/ci.yml/badge.svg)](https://github.com/xwojziarnik/job-application-tracker/actions/workflows/ci.yml)

REST API for tracking job applications: companies, job offers, application status history,
interviews and notes. Built as a production-style backend project with a focus on clean
architecture, testing and security.

**Stack:** Python 3.14 · FastAPI · SQLAlchemy 2.0 (async) · PostgreSQL 17 · Alembic ·
Pydantic v2 · pytest · Docker

## Features

**Available now (stage 1: project skeleton)**

- Async FastAPI application with an app factory and lifespan-managed database engine
- Health checks for the process and the database
- Alembic migrations (async) with deterministic constraint naming
- Unit and integration tests against a real PostgreSQL (testcontainers)
- CI with linting, type checking, tests and dependency vulnerability scanning

**Planned**

- Companies, job offers and tags
- Applications with a validated status workflow and full status history
- Interviews, contacts and notes, with a timeline per application
- Filtering and search (e.g. applications with no response for 14 days)
- Statistics: recruitment funnel, effectiveness of job boards, response times
- JWT authentication (single user first)

See the [roadmap](#roadmap) for the order of work.

## Quick start (Docker)

```bash
cp .env.example .env
docker compose up --build
```

- API: http://localhost:8000
- Interactive docs (Swagger UI): http://localhost:8000/docs
- Alternative docs (ReDoc): http://localhost:8000/redoc

Migrations run automatically when the `api` container starts. If ports 8000 or 5432 are
already taken, set `API_PORT` / `DB_PORT` in `.env`.
Ports are published on `127.0.0.1` only, so the API and the database are not reachable
from other machines on the network.

`docker compose up` also loads [`docker-compose.override.yml`](docker-compose.override.yml),
which is meant for development: it mounts `src/` and `migrations/` into the container and
runs uvicorn with `--reload`, so code changes apply without rebuilding the image. To run the
production configuration (no reload, no mounted code):

```bash
docker compose -f docker-compose.yml up --build
```

## Local development

Requires Python 3.13+ (3.14 recommended) and Docker.

```bash
pip install -e . --group dev   # app + dev tools (pip 25.1+ for --group)
pre-commit install             # ruff checks on every commit
cp .env.example .env
docker compose up -d db        # PostgreSQL only
alembic upgrade head
uvicorn job_tracker.main:app --reload
```

## Configuration

Settings are read from environment variables or a `.env` file
(see [`.env.example`](.env.example) and
[`core/config.py`](src/job_tracker/core/config.py)).

| Variable        | Default                                                       | Description                                       |
|-----------------|---------------------------------------------------------------|---------------------------------------------------|
| `ENVIRONMENT`   | `local`                                                       | `local`, `test` or `production`                   |
| `DEBUG`         | `false`                                                       | FastAPI debug mode                                |
| `DATABASE_URL`  | `postgresql+asyncpg://tracker:tracker@localhost:5432/tracker` | Async SQLAlchemy URL; **required in production**  |
| `DATABASE_ECHO` | `false`                                                       | Log SQL statements                                |
| `BIND_HOST`     | `127.0.0.1`                                                   | Host interface for published ports (Docker Compose only) |
| `API_PORT`      | `8000`                                                        | Host port for the API (Docker Compose only)       |
| `DB_PORT`       | `5432`                                                        | Host port for PostgreSQL (Docker Compose only)    |

With `ENVIRONMENT=production` the app refuses to start unless `DATABASE_URL` is set
explicitly, so the local default credentials can never be used by accident.

## API

All endpoints are versioned under `/api/v1`. Full, always up-to-date documentation is
generated by FastAPI at `/docs`.

| Method | Path                | Description                                        |
|--------|---------------------|----------------------------------------------------|
| GET    | `/api/v1/health`    | Liveness: the process is up                        |
| GET    | `/api/v1/health/db` | Readiness: the database is reachable (503 if not)  |

Domain errors are returned in a consistent format:

```json
{"error": {"code": "not_found", "message": "Application 42 not found"}}
```

## Architecture

Layered architecture with a single direction of dependencies:

```
api (FastAPI routers)  →  services (business logic)  →  repositories (DB access)  →  models
         ↕
   schemas (Pydantic request/response models)
```

- Routers stay thin: they validate input and call a service.
- Services contain business rules and know nothing about HTTP, which keeps them easy to test.
- Repositories hide SQLAlchemy; the session is injected with FastAPI dependencies.
- Domain exceptions are mapped to HTTP responses by one global handler.

```
src/job_tracker/
├── api/            # FastAPI routers and dependencies
├── core/           # settings, exceptions
├── db/             # declarative base, engine and sessions
├── models/         # SQLAlchemy models
├── schemas/        # Pydantic request/response models
├── repositories/   # database access
└── services/       # business logic
migrations/         # Alembic
tests/              # unit/ and integration/
```

## Testing and quality checks

```bash
ruff check . && ruff format --check .   # lint (incl. security rules) and formatting
mypy                                    # strict type checking
pytest                                  # unit and integration tests
pip-audit --skip-editable               # known vulnerabilities in installed packages
```

Integration tests start a throwaway PostgreSQL with
[testcontainers](https://testcontainers.com/). Locally they are skipped when Docker is not
running; in CI a missing Docker fails the build.

## Security

- **Code:** ruff security rules (`S`, the bandit rule set) run on every lint.
- **Dependencies:** `pip-audit` runs in CI on every push and pull request, and weekly to catch
  newly published vulnerabilities.
- **Updates:** Dependabot opens weekly PRs for Python packages and GitHub Actions.
- **Supply chain:** GitHub Actions are pinned to commit SHAs; the CI token is read-only.
- **Configuration:** secrets come only from the environment; `.env` is gitignored, and
  production requires an explicit `DATABASE_URL`.
- **Runtime:** the Docker image runs as a non-root user; error responses do not expose
  internal details.

## CI

GitHub Actions ([`ci.yml`](.github/workflows/ci.yml)) runs on pushes to `main`, on pull
requests and weekly:

1. Install dependencies
2. Dependency audit (`pip-audit`)
3. Lint and formatting (`ruff`)
4. Changelog format check
5. Type check (`mypy`)
6. Tests (`pytest`, including integration tests)
7. Release (on `main` only, see [Releases and changelog](#releases-and-changelog))

## Migrations

```bash
alembic revision --autogenerate -m "describe change"   # after changing models
alembic upgrade head                                   # apply
alembic downgrade -1                                   # roll back one revision
```

New models must be imported in [`models/__init__.py`](src/job_tracker/models/__init__.py)
so that autogenerate can see them.

## Releases and changelog

Changes are recorded in [`CHANGELOG.md`](CHANGELOG.md) following
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Every change goes under
`[Unreleased]`, in one of the subsections `Added`, `Changed`, `Deprecated`, `Removed`,
`Fixed` or `Security`. CI validates the file on every run.

Versions follow [Semantic Versioning](https://semver.org/) and are managed by
[hatch](https://hatch.pypa.io/) in [`src/job_tracker/__init__.py`](src/job_tracker/__init__.py).
A push to `main` releases a new version when a commit subject ends with a marker:

| Commit subject ends with | Version change   | Example                                 |
|--------------------------|------------------|-----------------------------------------|
| `[major]`                | `1.4.2 → 2.0.0`  | `refactor: drop API v1 [major]`         |
| `[minor]`                | `1.4.2 → 1.5.0`  | `feat: add interview notes [minor]`     |
| `[fix]`                  | `1.4.2 → 1.4.3`  | `fix: reject negative salary [fix]`     |

When a push contains several markers, the highest one wins. The release job then:

1. bumps the version with `hatch version <major|minor|fix>`,
2. renames `[Unreleased]` to the new version with today's date, drops empty subsections and
   starts a fresh `[Unreleased]` section,
3. regenerates the comparison links at the end of the changelog,
4. commits the change as `chore(release): vX.Y.Z [skip ci]` and pushes it with a `vX.Y.Z` tag.

The release fails when `[Unreleased]` is empty, so describe changes before merging.
The logic lives in [`scripts/release.py`](scripts/release.py).
