# Design decisions

Architecture decisions for the job-application-tracker, recorded before implementing
stage 2 (companies, job offers, applications). Each decision lists the context, the options
with their trade-offs, a recommendation and the final choice.

**How to use this file:** fill in **Decision** and **Rationale** for every entry, then change
its status from `Proposed` to `Accepted`. When a decision is changed later, do not edit the
old text: mark it `Superseded by D-XX` and add a new entry, so the history stays readable.

## D-01: Primary key type

**Status:** Accepted (2026-10-26)

**Context.** Every table needs a primary key, and the ID appears in URLs such as
`/api/v1/offers/{id}`. The choice affects security, performance and how readable the data is
while debugging.

| Option | Pros | Cons |
|---|---|---|
| `int` / `BIGINT` identity | Small, fast indexes; readable (`/offers/42`); natural ordering | Reveals the number of records; IDs are guessable (enumeration), so authorisation must be perfect |
| `UUID` v4 | Not guessable; can be generated by the client or app before insert | 16 bytes; random values fragment B-tree indexes; harder to read |
| `UUID` v7 | Not guessable *and* time-ordered, so indexes stay compact | Generated in Python (`uuid.uuid7()` since 3.14), as PostgreSQL 17 has no built-in `uuidv7()` (added in 18); still less readable than int |
| `int` internally + public UUID column | Fast joins, safe public IDs | Two identifiers to keep consistent; more code |

**Questions to answer.**
- Will the API ever be multi-user? (Stage 4 adds JWT; guessable IDs plus a missing ownership
  check is a classic IDOR vulnerability.)
- Do you need to create IDs before inserting (e.g. offline import)?

**Recommendation.** `UUID` v7. It removes ID enumeration as a class of problems before
multi-user support arrives and keeps index performance close to integers.

**Decision.** UUID **v4** for every primary key, generated in Python (`uuid.uuid4()`) and
defined once in a reusable primary-key mixin in `db/base.py` (next to `TimestampMixin`),
so all models share it and the UUID version can be changed in one place.

**Rationale.** A v4 UUID is 122 random bits from a cryptographic generator: it reveals
nothing (no creation time, no order) and cannot be guessed. Index fragmentation, the main
cost of v4, only matters at millions of rows; this tracker will hold hundreds. Obfuscating
v7 IDs (e.g. encrypting the timestamp) was rejected: key management and ID translation in
every endpoint for no practical gain.

**Consequences.**
- No natural ordering by ID; lists are sorted by `created_at` or another explicit column.
- Unpredictable IDs are defence in depth only; ownership checks (stage 4) remain mandatory.

## D-02: Enum storage in PostgreSQL

**Status:** Accepted (2026-10-26)

**Context.** Several fields have a fixed set of values: work mode, seniority, contract type,
currency, offer source and application status. Python uses `enum.StrEnum` either way; the
question is how the database stores them.

| Option | Pros | Cons |
|---|---|---|
| Native PostgreSQL `ENUM` | Type-safe at DB level; compact | Adding a value needs a special migration (`ALTER TYPE ... ADD VALUE`, historically not in a transaction); removing or renaming a value is painful; Alembic autogenerate does not detect value changes |
| `VARCHAR` + `CHECK` constraint | Easy to change in a normal migration; still validated by the DB | Constraint must be updated by hand when values change |
| `VARCHAR` without constraint | Simplest | Only the application validates; bad data possible via direct SQL |
| Lookup table (e.g. `sources`) | Values editable at runtime without deploy | Extra joins and endpoints; overkill for fixed sets |

**Questions to answer.**
- Which sets will change? Offer sources and statuses are likely to grow; work mode is stable.

**Recommendation.** `VARCHAR` + `CHECK` for all of them (SQLAlchemy `Enum(...,
native_enum=False)` generates this). Consider a lookup table only for offer sources if you
want to add new job boards without a deploy.

**Decision.** `VARCHAR` + `CHECK` constraint for all fixed sets of values (work mode,
seniority, currency, salary period, offer source, application status), mapped to
`enum.StrEnum` in Python.

**Rationale.** Values can be added or removed with an ordinary migration, and the database
still rejects invalid data, unlike a plain `VARCHAR`.

**Implementation notes.**
- With `native_enum=False`, SQLAlchemy does **not** create the `CHECK` unless
  `create_constraint=True` is set.
- Every enum needs a `name`, because the `ck` naming convention requires one.
- Alembic autogenerate does not detect changes to `CHECK` constraints: when a value is added
  or removed, write that migration by hand (drop and recreate the constraint).

- Enum **values** (`remote`) are stored, not member names (`REMOTE`), which SQLAlchemy
  stores by default; configure `values_callable` accordingly. The database, the API and the
  Python code then use the same strings, and renaming a Python member cannot break
  existing rows.

## D-03: Money and salary representation

**Status:** Accepted (2026-10-26)

**Context.** Offers show salary ranges that differ in currency, period (monthly, hourly,
yearly) and gross/net (B2B net vs. employment contract gross). The statistics in stage 5
will compare them.

| Option | Pros | Cons |
|---|---|---|
| `Integer` in whole currency units | Simple; salaries are rarely fractional | Cannot store hourly rates like 137.50 |
| `Integer` in minor units (grosze, cents) | Exact; standard in payment systems | Easy to forget the ×100 conversion in the API |
| `Numeric(12, 2)` ↔ `Decimal` | Exact; natural for hourly rates | Slightly more ceremony in Pydantic (serialisation as string or number) |
| `Float` | — | **Never for money:** rounding errors |

**Also decide:**
- Which fields: `salary_min`, `salary_max`, `currency`, `salary_period`
  (`month`/`hour`/`year`), and whether the amount is gross or net (often implied by contract
  type).
- Whether one offer can have several ranges (e.g. B2B *and* employment contract). If yes,
  this becomes a separate `salary_ranges` table.
- Currency as ISO 4217 code (`PLN`, `EUR`, `USD`) validated against an allow list.

**Recommendation.** `Numeric(12, 2)` with `Decimal`, plus `currency` and `salary_period`
columns and a `CHECK (salary_min <= salary_max)`. One range per offer in stage 2; move to a
separate table only if real offers need it.

**Decision.** At this stage the app tracks **B2B offers only**, and the salary is always
stored as a **net monthly B2B rate**: `salary_min` and `salary_max` as `int` in whole
currency units, plus `currency` (ISO 4217 code, `VARCHAR(3)` + `CHECK` with an allow list,
per D-02). One range per offer.

**Rationale.** The owner runs a sole proprietorship (JDG), so only B2B offers are relevant.
With a single, fixed period and contract type, every stored amount is directly comparable,
and monthly amounts do not need fractions, so whole units in `int` are exact enough.

**Consequences.**
- Offers quoting an **hourly** rate are converted to a monthly amount when they are entered,
  using **160 hours per month** (e.g. 150 PLN/h → 24 000 PLN/month).
- Offers quoting only employment-contract (UoP) gross salaries are out of scope for now.
- Salary is **optional**: offers without published pay are stored with empty amounts.
- Constraints: `salary_min <= salary_max`, both amounts positive; when an amount is present,
  `currency` is required.
- Supporting other contract types or hourly rates later means adding `contract_type` and
  `salary_period` columns (or a separate `salary_ranges` table) and a new decision entry.

## D-04: Deleting records with dependants

**Status:** Accepted (2026-10-26)

**Context.** Company → offers → application form a chain. Deleting a parent must not leave
orphans, and should not silently destroy history you care about.

| Option | Pros | Cons |
|---|---|---|
| `ON DELETE CASCADE` | Simple; one call cleans everything | One mistaken `DELETE /companies/{id}` erases all offers and applications |
| `ON DELETE RESTRICT` + `409 Conflict` | Safe; the client must delete children first | More requests to clean up |
| Soft delete (`deleted_at` column) | Recoverable; keeps history for statistics | Every query must filter deleted rows; unique constraints need partial indexes |
| Archiving (`is_archived`) instead of deleting | Matches the real use case ("I'm no longer interested") | Not a real delete; still need a delete for mistakes |

**Questions to answer.**
- Will you want statistics that include rejected or abandoned applications? (Probably yes;
  that argues against hard deletes of applications.)

**Recommendation.** `RESTRICT` (→ 409 with a clear message) for company → offers and
offer → application. Hard delete only for genuine mistakes. Model "no longer relevant" as
an application status (`WITHDRAWN`) rather than a delete. Revisit soft delete if you need
an undo feature.

**Decision.** Companies are **never deleted**. Instead they are marked inactive with an
`is_active` flag (default `true`). There is no `DELETE /companies/{id}` endpoint;
deactivation and reactivation go through an update of the company.

**Rationale.** Deleting a company would erase its offers and the full history of
applications to it, which the statistics in stage 5 depend on. Deactivation keeps the
history and is reversible.

**Consequences.**
- The foreign key offer → company uses `ON DELETE RESTRICT`, so even a manual `DELETE`
  in SQL cannot silently remove history.
- Company lists show active companies by default, with a filter to include inactive ones.
- Offers of an inactive company are **hidden** from offer lists by default (the same filter
  applies); the data stays in the database.
- Offers and applications **can be deleted**, e.g. to fix a mistake. Deleting an offer also
  deletes its applications (`ON DELETE CASCADE`, with `passive_deletes=True` in the ORM).
- The unique name index (D-05) covers inactive companies too: adding a company that already
  exists as inactive should lead to reactivating it, not to a duplicate.

## D-05: Uniqueness and case sensitivity

**Status:** Accepted (2026-10-26)

**Context.** Duplicates make statistics wrong. Offers will often be added through an AI
session from job board links, so the same offer may be submitted twice.

| Field | Options | Things to watch |
|---|---|---|
| Company name | unique as-is / unique case-insensitive / not unique | "Allegro", "allegro" and "Allegro " (trailing space); companies with the same name in different countries |
| Offer URL | unique / unique after normalisation / not unique | Tracking parameters (`?utm_source=...`), trailing slashes, `http` vs `https`; the same offer reposted under a new URL |
| Tag name | unique after normalisation | See D-09 |

**Implementation notes.**
- Case-insensitive uniqueness: a unique index on `lower(name)`, or the `citext` extension.
- Strip whitespace in Pydantic before the value reaches the database.
- Always handle `IntegrityError` from the database and map it to `409`. A "check, then
  insert" is not enough: two concurrent requests can both pass the check.

**Recommendation.** Company name: unique, case-insensitive, trimmed. Offer URL: unique
after normalisation (lower-case host, no tracking query parameters, no trailing slash).

**Decision.**
- **Company name:** trimmed, unique case-insensitively through a unique index on
  `lower(name)`.
- **Offer URL:** normalised before saving (lower-case scheme and host, tracking parameters
  such as `utm_*` removed, no trailing slash) and unique.
- A unique violation from the database (`IntegrityError`) is mapped to `409 Conflict` with
  a clear message.

**Rationale.** Offers are often added through an AI-assisted session from job board links,
so the same company or offer can easily be submitted twice in a slightly different form.
Duplicates would distort the statistics.

**Implementation notes.**
- The `lower(name)` index is an index on an expression; Alembic autogenerate has limited
  support for these, so review the generated migration.
- URL normalisation lives in one function, used by both the schema validation and the
  service, and is covered by unit tests.

## D-06: Job offer ↔ application cardinality

**Status:** Accepted (2026-10-26)

**Context.** An application is your response to one offer. The question is whether one offer
can have more than one application.

| Option | Pros | Cons |
|---|---|---|
| 1:1 (unique `job_offer_id` in `applications`) | Simple; impossible to apply twice by mistake | Re-applying to the same offer months later needs a new offer record |
| 1:N | Models re-applications and multiple attempts | Lists and statistics must decide which application counts |
| Merge application fields into the offer | Fewer tables | Mixes "what the company posted" with "what I did"; harder to add history in stage 3 |

**Recommendation.** 1:1 for now, enforced by a unique constraint. Re-applying is rare and
the company usually posts a new offer anyway.

**Decision.** **1:N**: an offer can have several applications over time, but **at most one
active application** at a time. An application is active while its status is not final
(`REJECTED`, `WITHDRAWN`, `GHOSTED`, `ACCEPTED`). The rule is enforced in the database by
a **partial unique index** on `job_offer_id` limited to rows with a non-final status.

**Rationale.** Re-applying to the same offer after a rejection happens and should be
recorded, while two parallel applications to one offer would be a data error. Enforcing
it in the database also covers concurrent requests.

**Consequences.**
- A new application for an offer with an active one returns `409 Conflict`.
- The set of final statuses lives in one place in the code and must match the index
  condition; changing it requires a migration.
- Lists and statistics must decide which application counts for an offer (e.g. the latest).

## D-07: Transaction ownership

**Status:** Accepted (2026-10-26)

**Context.** Someone has to call `commit()`. If every layer can commit, a service that
touches two tables (e.g. offer + tags) can end up half-saved after an error.

| Option | Pros | Cons |
|---|---|---|
| Repositories commit | Simple at first | Multi-step operations are not atomic; hard to test |
| Services commit (unit of work per use case) | One use case = one transaction; explicit | Every service method must remember to commit |
| Session dependency commits at the end of the request, rolls back on error | Nothing to remember; always atomic per request | Commit happens after the handler returns, so DB errors (e.g. unique violations) surface late unless you `flush()` in the service |

**Recommendation.** Repositories only `add()` and `flush()`; the **service** decides when to
commit. Flushing early lets the service catch `IntegrityError` and turn it into a domain
error with a clear message.

**Decision.** Repositories only `add()` and `flush()`; they never commit. Each **service**
method is one use case and one transaction, and the service decides when to commit.

**Rationale.** Multi-step operations (e.g. an offer with its tags) are atomic: either
everything is saved or nothing. Flushing inside the service makes the database check its
constraints early, so the service can catch `IntegrityError` and turn it into a domain error
(`ConflictError` → `409`) with a clear message before committing.

**Consequences.**
- Every service method that writes must end with an explicit commit; a forgotten commit
  shows up in integration tests, which go through the real database.
- `flush` is not `commit`: flushed changes are visible only inside the current transaction
  until it is committed.

## D-08: Pagination style

**Status:** Accepted (2026-10-26)

**Context.** Every list endpoint needs pagination with an upper limit, so a single request
cannot load the whole table.

| Option | Pros | Cons |
|---|---|---|
| `limit` / `offset` | Simple; can jump to page N; easy `total` | Slow for large offsets; items can shift between pages while data changes |
| Cursor (keyset) | Fast and stable on large data sets | No "jump to page N"; more complex; sorting must be by unique keys |

**Also decide:** the response shape (`items`, `total`, `limit`, `offset`), the default
`limit` (e.g. 20) and the maximum (e.g. 100), and whether to return `total` (an extra
`COUNT` query).

**Recommendation.** `limit`/`offset` with a maximum of 100. A personal tracker will hold
hundreds of rows, not millions; keyset pagination would be premature.

**Decision.** `limit`/`offset` pagination on every list endpoint: default `limit` 20,
maximum 100 (a larger value is rejected with `422`). Responses include `total`:
`{"items": [...], "total": 57, "limit": 20, "offset": 0}`.

**Rationale.** A personal tracker holds hundreds of rows, so offset pagination is fast enough
and allows jumping to any page; `total` makes paging in a client straightforward. The upper
limit prevents loading a whole table in one request.

**Consequences.**
- Every list runs two queries (the page and a `COUNT`); acceptable at this scale.
- Lists need a deterministic sort order (e.g. `created_at` then `id`), otherwise rows can
  repeat or disappear between pages.

## D-09: Tag normalisation

**Status:** Accepted (2026-10-26)

**Context.** Tags like `FastAPI`, `fastapi` and ` fast-api ` should not become three
different tags, or filtering by tag stops working.

**Options to consider.**
- Lower-case and trim only.
- Also replace spaces and underscores with `-` (slug).
- Allow list of known tags vs. free tags created on the fly.
- Maximum length and allowed characters (e.g. `[a-z0-9.+#-]`, so that `c++`, `c#` and
  `.net` still work).

**Watch out for:** creating tags inside offer creation ("get or create") under concurrent
requests. Use `INSERT ... ON CONFLICT DO NOTHING` and then select, instead of
"select, then insert".

**Recommendation.** Free tags, lower-case, trimmed, internal whitespace collapsed to `-`,
max 50 characters, restricted character set.

**Decision.** **Free tags**, created on the fly when an offer is saved, and normalised before
saving:
1. lower-case, trimmed, internal whitespace collapsed to `-` (`Machine Learning` →
   `machine-learning`);
2. allowed characters: `a–z`, `0–9`, `.`, `+`, `#`, `-` (so `c++`, `c#`, `.net`, `node.js`
   work); anything else is rejected with `422`;
3. maximum length 50 characters.

**Rationale.** Free tags need no upfront list and fit the AI-assisted way offers are added,
while normalisation keeps `FastAPI`, `fastapi` and ` fastapi ` as one tag, so filtering by
tag stays reliable.

**Implementation notes.**
- Normalisation lives in one function, covered by unit tests, used before every lookup
  and insert.
- "Get or create" for tags uses `INSERT ... ON CONFLICT DO NOTHING` followed by a select,
  not "select, then insert", which races under concurrent requests.

## D-10: Creating a company together with an offer

**Status:** Accepted (2026-10-26)

**Context.** Offers will mostly be added through an AI-assisted session from job board links.
Requiring the company to exist first means two calls per offer; allowing inline creation is
convenient but mixes responsibilities.

| Option | Pros | Cons |
|---|---|---|
| `company_id` only | Clean, explicit API; one responsibility per endpoint | Two requests per new company |
| `company_id` **or** `company_name` (get or create) | One request; ideal for the AI-assisted flow | Typos create duplicate companies (mitigated by D-05) |
| Separate `PUT /companies/by-name/{name}` (idempotent upsert) | Clean API and still one extra call | Unusual endpoint shape |

**Recommendation.** `company_id` only in `POST /offers`, plus an idempotent
"get or create company by name" operation that returns the existing company when the
(normalised) name already exists.

**Decision.** `POST /offers` accepts **`company_id` only**. A separate, idempotent
"get or create company by name" operation returns the existing company when the normalised
name already exists (D-05), or creates it. If the matching company is **inactive** (D-04),
the operation fails with `409 Conflict` and a message saying the company is inactive and
must be activated first; it is never reactivated automatically.

**Rationale.** Each endpoint has one responsibility, and the AI-assisted flow stays simple:
get or create the company, then create the offer with its ID. Refusing to reactivate
silently keeps deactivation an explicit, deliberate state.

**Consequences.**
- Creating an offer for an inactive company is rejected the same way (`409`), with the same
  message.
- The error response should carry a dedicated error code (e.g. `company_inactive`), so a
  client can tell it apart from a duplicate.

## D-11: Dates, times and time zones

**Status:** Accepted (2026-10-26)

**Context.** Applications have dates (sent, posted, interview). Statistics in stage 5 depend
on correct durations ("time to first response").

**Decide:**
- Timestamps: `TIMESTAMP WITH TIME ZONE`, stored in UTC (already used by `TimestampMixin`).
- Calendar dates without time (offer posting date, `applied_on`): `DATE` vs. timestamp.
- Validation rules: `applied_on` not in the future; an interview not before the application.
- How the API returns times: ISO 8601 with offset (`2026-10-26T18:00:00Z`).

**Recommendation.** Timezone-aware UTC timestamps for events, `DATE` for pure calendar
dates, and timezone conversion only at the edges (the client).

**Decision.**
- **Events** (record creation and updates, status changes, interview times):
  `TIMESTAMP WITH TIME ZONE`, stored in UTC.
- **Calendar dates** (application sent date, offer posting date): `DATE`, with no time and
  no time zone.
- The API uses ISO 8601: `2026-10-26` for dates, `2026-10-26T18:00:00Z` for timestamps.
- Validation: the application sent date cannot be in the future; an offer's posting date
  cannot be later than the sent date of an application to it.

**Rationale.** "I applied on 26 October" is a calendar fact without a time zone, while events
need exact instants for the duration statistics in stage 5. Storing UTC avoids errors around
daylight saving changes; conversion to local time happens only in the client.

**Consequences.**
- "Today" for the future-date check must be computed in one agreed time zone
  (e.g. `Europe/Warsaw`), otherwise an application sent shortly after midnight could be
  rejected.

## D-12: Test database isolation

**Status:** Accepted (2026-10-26)

**Context.** Integration tests share one PostgreSQL container per session. Without isolation,
data from one test leaks into the next and tests become order-dependent.

| Option | Pros | Cons |
|---|---|---|
| Transaction per test, rolled back at the end | Very fast; nothing to clean up | The app's session must join the outer transaction; code that calls `commit()` needs savepoints (`join_transaction_mode="create_savepoint"`) |
| `TRUNCATE ... RESTART IDENTITY CASCADE` after each test | Simple; tests run exactly like production code | Slower as the number of tables grows |
| New database per test (template database) | Perfect isolation | Slowest; most setup |

**Also decide:** schema creation via `alembic upgrade head` once per session (tests the
migrations too) vs. `Base.metadata.create_all` (faster, but does not test migrations).

**Recommendation.** `alembic upgrade head` once per session plus a rolled-back transaction
per test using savepoints. Fall back to `TRUNCATE` if the savepoint setup gets in the way.

**Decision.** **A separate database for every test.** Migrations run once per test session
(`alembic upgrade head`) into a template database; each test gets a fresh copy created with
`CREATE DATABASE ... TEMPLATE ...` and dropped afterwards. The app under test is configured
with that database's URL.

**Rationale.** Perfect isolation: every test starts from exactly the migrated schema, and
the application code (including its commits) runs with no test-specific transaction tricks.
Running migrations once also tests them.

**Consequences.**
- The slowest of the options: cloning a database takes noticeably longer than a rollback,
  so the suite grows slower with the number of tests. Revisit (rollback with savepoints) if
  it becomes a problem.
- PostgreSQL refuses to clone a template that has open connections: after migrating, all
  connections to the template must be closed (dispose the engine).
- Each test's engine must be disposed before its database is dropped, or `DROP DATABASE`
  fails on active connections.
- Database names must be unique per test (e.g. a random suffix), so tests can later run in
  parallel.

## D-13: Error response format

**Status:** Accepted (2026-10-26); refined by D-17, which replaces the `internal_error`
code with `internal_server_error`

**Context.** Out of the box the API returns errors in three shapes: domain errors
(`{"error": {...}}`), `HTTPException` (`{"detail": "..."}`) and validation errors
(`{"detail": [{"loc": ..., "msg": ..., "type": ...}]}`). Clients, including the AI-assisted
session that adds offers, would have to handle all three.

| Option | Pros | Cons |
|---|---|---|
| One custom format for everything | One shape to handle; full control over what is exposed | Exception handlers for validation and HTTP errors must be written and tested |
| FastAPI defaults + custom domain errors | No extra code | Three shapes for clients |
| RFC 9457 Problem Details | Standard (`application/problem+json`) | More fields than needed for a single-client API |

**Decision.** **One format for every error**, including validation errors (`422`) and
`HTTPException`:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Request validation failed",
    "details": [
      {"field": "salary_max", "message": "must be greater than or equal to salary_min"}
    ]
  }
}
```

- `code`: stable, machine-readable, snake_case (`validation_error`, `not_found`,
  `conflict`, `company_inactive`, `internal_error`, ...).
- `message`: human-readable summary.
- `details`: optional list, used for field-level validation errors.

**Rationale.** Clients branch on `code` alone, whatever produced the error. Owning the
format also decides what is exposed: no stack traces, SQL or internal exception messages.

**Consequences.**
- Handlers are registered for `DomainError`, `RequestValidationError` and Starlette's
  `HTTPException` (which also covers 404 for unknown routes and 405), plus a catch-all
  for unexpected exceptions that returns `500` with `internal_error` and a generic message,
  while the details go only to the server log.
- Validation details must not echo the rejected input back (it could contain secrets or
  very long values); only the field path and the reason.
- The existing `/health/db` endpoint and its tests change to the new format.

## D-14: Allowed values of enumerations

**Status:** Accepted (2026-10-26); the seniority part is superseded by D-15

**Context.** D-02 decided how enumerations are stored; this entry fixes their values.
Values are stored as lower-case strings (D-02), so they are listed in that form.

**Decision.**

| Enumeration | Values |
|---|---|
| Offer source | `linkedin`, `justjoinit`, `nofluffjobs`, `pracuj`, `bulldogjob`, `company_website` |
| Seniority | `junior`, `mid`, `senior`, `lead` |
| Work mode | `remote`, `hybrid`, `office` |
| Currency | `PLN`, `EUR`, `USD` (ISO 4217 codes are upper-case by definition) |

- **Offer source:** job boards by name, plus `company_website` for offers found on a
  company's careers page. There is no `other` value: a new job board is added with a
  migration (D-02).
- **Seniority is a range:** each offer has `seniority_min` and `seniority_max`
  (e.g. `mid`–`senior`); a single-level offer has both set to the same value.

**Rationale.** Closed lists keep the statistics clean (no `LinkedIn` vs `linkedin.com`)
and match the job boards actually used.

**Consequences.**
- Seniority has an order (`junior` < `mid` < `senior` < `lead`) that strings do not have
  (alphabetically `lead` < `mid`). The rule `seniority_min <= seniority_max` must use that
  order: in Python (e.g. an ordered enum) and, if enforced in the database, through a
  `CHECK` that maps each value to its rank.
- Filtering offers by seniority (e.g. "offers for a mid") means
  `seniority_min <= mid <= seniority_max`, which also relies on the rank.

## D-15: Seniority as one combined value

**Status:** Accepted (2026-10-26). Supersedes the seniority part of D-14.

**Context.** D-14 modelled seniority as a range of two fields (`seniority_min`,
`seniority_max`). That needs a rank-aware `CHECK`, rank-aware filtering and two fields to
fill for every offer, while job boards publish seniority as one label such as "Mid/Senior".

**Decision.** One field, `seniority`, with **single and combined values** of adjacent levels:

| Value | Meaning |
|---|---|
| `junior` | Junior |
| `junior_mid` | Junior/Mid |
| `mid` | Mid (Regular) |
| `mid_senior` | Mid/Senior |
| `senior` | Senior |
| `senior_lead` | Senior/Lead |
| `lead` | Lead |

Stored as `VARCHAR` + `CHECK` like every other enumeration (D-02).

**Rationale.** Matches how offers are actually labelled, so entering an offer is a direct
copy of what the job board shows. One field, one constraint, and no ordering rule between
two columns.

**Consequences.**
- Combinations of non-adjacent levels (e.g. junior–senior) cannot be expressed; such offers
  use the closest combined value.
- Filtering by a level must include the combined values that contain it: "offers for
  a mid" means `junior_mid`, `mid` and `mid_senior`. Keep this mapping in one place in the
  code (e.g. a method on the enum) and cover it with unit tests.
- If a new level is added later (e.g. `principal`), its combined values are added with it,
  in a migration (D-02).

## D-16: Application statuses

**Status:** Accepted (2026-10-26)

**Context.** D-06 relies on the difference between active and final statuses, and stage 3
adds a status workflow with history. The full list of statuses is fixed here; values are
lower-case strings (D-02).

**Decision.**

| Group | Status | Meaning |
|---|---|---|
| Active | `draft` | Prepared, not sent yet |
| Active | `applied` | Application sent |
| Active | `screening` | First contact or HR interview |
| Active | `technical` | Technical interview |
| Active | `task` | Take-home task or live coding |
| Active | `final` | Final interview |
| Active | `offer` | Offer received, decision pending |
| Active | `on_hold` | Recruitment paused by the company or by the candidate |
| Final | `accepted` | Offer accepted |
| Final | `rejected` | Rejected by the company, or offer declined |
| Final | `withdrawn` | Withdrawn by the candidate |
| Final | `ghosted` | No response from the company |

**Rationale.** Covers the typical recruitment process for backend roles. `on_hold` is
**active**: a paused recruitment can still continue, so it blocks a second application to
the same offer (D-06).

**Consequences.**
- The set of final statuses (`accepted`, `rejected`, `withdrawn`, `ghosted`) is defined in
  one place in the code and must match the condition of the partial unique index from D-06.
- Allowed transitions between statuses (e.g. from `on_hold` back to the stage it paused)
  are decided in stage 3, together with the status history.
- In stage 2 the status is set on creation and is not editable through `PATCH`
  (see the stage 2 roadmap).

## D-17: Error format details

**Status:** Accepted (2026-10-29). Refines D-13 and replaces its `internal_error` code.

**Context.** D-13 fixed the shape of every error response. Implementing the handlers raised
questions it left open: what to send when there are no details, how to name a field in a
validation error, which codes to give errors that come from the framework rather than from
our own domain errors, and how to keep the original cause of an error without exposing it.

| Question | Options considered | Choice |
|---|---|---|
| No field-level details | omit the key; `"details": null`; `"details": []` | Omit the key |
| Name of an invalid field | `salary_max`; `body.salary_max` (with source) | Path without its source |
| Unreachable database | generic `service_unavailable`; dedicated code | Dedicated `database_unavailable` |
| Code of an `HTTPException` | always `http_error`; derived from the status | Derived from the status |
| Code of an unexpected error (500) | `internal_error` (D-13); `internal_server_error` | `internal_server_error` |

**Decision.**

- **`details` is omitted** when there are no field-level details; it is never `null` or an
  empty list.
- **Field path:** the location of the invalid value without its source (`body`, `query`,
  `path`, `header`), joined with dots: `tags.1.name`, `salary_max`, `limit`. When nothing is
  left after removing the source (an error on the whole model) and for invalid JSON (whose
  location is only a character position), the field is the source itself, e.g. `body`.
  The `"Value error, "` prefix Pydantic adds to errors from custom validators is removed.
- **Domain errors form categories:** a category (`NotFoundError` 404, `ConflictError` 409,
  `ServiceUnavailableError` 503) defines the status, a code and a default message; a
  specific error (e.g. `CompanyInactiveError`, `DatabaseUnavailableError`) inherits the
  status and overrides the code. The status says what kind of error it is, the code which
  one exactly.
- **`HTTPException` codes are derived from the status phrase** in snake_case: `not_found`,
  `method_not_allowed`, `too_many_requests`; `http_error` for a status outside the standard.
  A string `detail` becomes the message; any other `detail` is not exposed. Headers such as
  `Allow` (405) and `WWW-Authenticate` (401) are kept.
- **Unexpected exceptions return `internal_server_error`**, the same code an explicit
  `HTTPException(500)` gets, so a status never has two codes.
- **Logging:** server-side errors (domain errors with a 5xx status and unexpected
  exceptions) are logged with the traceback, including the original cause chained with
  `raise ... from`; unexpected exceptions also with the request method and path (without
  the query string). Client errors (4xx) are not logged.

**Rationale.** Clients branch on `code` alone, so every distinct situation needs its own
stable code, and one status must not have two codes. Leaving out the source of a field
keeps the codes and paths short; a client knows from the endpoint what is in the body and
what in the query. Logging the cause keeps errors diagnosable while the response stays free
of internal details.

**Consequences.**
- Codes derived from status phrases depend on the Python version: Python 3.13 renamed some
  phrases after RFC 9110 (e.g. 422 is now "Unprocessable Content"). If a code must stay
  fixed, override it with an explicit mapping for that status.
- Messages of custom validators must describe the rule, not the value: anything placed in
  the message is sent to the client.
- Starlette re-raises an unexpected exception after the 500 response is sent, so the server
  logs it a second time; with `debug=True` it shows its own traceback page instead of the
  handler's response.

## D-18: Migration numbering

**Status:** Accepted (2026-10-30)

**Context.** Alembic gives every migration a random revision ID (e.g. `f712bc9b7594`), and
the file names started with the creation date. The order of migrations is visible only by
following `down_revision` from file to file.

| Option | Pros | Cons |
|---|---|---|
| Random IDs (Alembic default) | Branches can add migrations in parallel; Alembic merges heads | Order not visible in the file list or in `alembic_version` |
| Sequential numbers `001`, `002`, ... | Order visible at a glance; short, readable IDs | Two branches adding a migration get the same number |

**Decision.** Revision IDs are **sequential three-digit numbers** (`001`, `002`, ...) and
files are named `<number>_<slug>.py`, e.g. `001_create_companies.py`. The number is set
automatically by `process_revision_directives` in `migrations/env.py`;
`revision_environment = true` in `alembic.ini` makes it apply to hand-written migrations
as well.

**Rationale.** A single developer works in small pull requests, so parallel migrations are
rare, and a readable order is worth more than conflict-free IDs.

**Consequences.**
- Before merging a branch with a migration, the number must still be the next one; if
  `main` got a migration meanwhile, renumber the branch's migration (`revision`,
  `down_revision` and the file name). A unit test fails when there are several heads or
  the numbers are not consecutive.
- `alembic revision` runs `env.py` and connects to the database even without
  `--autogenerate`, so the database must be running.
- Three digits allow 999 migrations; beyond that the format must be widened.

## Deferred to each model

Decided while designing each model in its own slice (stage 2, steps 1–3), and recorded here
when made:

- **Required and optional fields** of each entity (`NOT NULL` constraints and Pydantic
  schemas).
- **PATCH semantics**: an omitted field means "do not change"; whether `null` clears a field
  and which fields may be cleared is decided per field.

### Company (2026-10-30)

| Field | Type | Required | Rules |
|---|---|---|---|
| `id` | UUID | set by the app | `UUIDPrimaryKeyMixin` (D-01) |
| `name` | text, 1–200 characters | yes | Trimmed; must not be empty after trimming; unique case-insensitively (D-05) |
| `website` | http(s) URL, up to 2048 characters | no | Validated as an `http`/`https` URL; not unique |
| `location` | text, up to 200 characters | no | Headquarters (city, country); where the job is done belongs to the offer |
| `industry` | text, up to 100 characters | no | Free text, e.g. `fintech` |
| `notes` | text, up to 2000 characters | no | Free notes |
| `is_active` | boolean | set by the app | `true` on creation; changed only through `PATCH` (D-04) |
| `created_at`, `updated_at` | timestamp | set by the database | `TimestampMixin` (D-11) |

- **Blank text in optional fields** (empty or only whitespace) is stored as `null`, so
  "no value" has one representation. All text fields are trimmed.
- **Create** (`POST`) accepts `name`, `website`, `location`, `industry` and `notes`; a new
  company is always active.
- **Update** (`PATCH`): an omitted field is not changed. `null` (or blank text) clears an
  optional field; `null` for `name` or `is_active` is rejected with `422`.
- **Read** returns every field above.
